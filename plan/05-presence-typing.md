# 05 — Presence, Typing, Read States

> Phase 2 (presence + typing) and Phase 8 (read states in Rust — Discord's most
> famous rewrite). Three features that look trivial and are quietly the best
> distributed-state teaching material in the whole project.

## 1. Presence (online/idle/dnd/offline) — the impossible-consistency feature

### Why it's hard
Presence is: *frequent writes × all-your-guilds fan-out × no persistence
allowed* (persisting presence = 100M+ writes/min at Discord scale; it's
intentionally ephemeral). It also has the **N×M fan-out problem**: when user U
changes status, every user sharing a guild with U may need an event — but you
must NOT send U's presence to everyone, only co-members. And the state is
reported, not requested: clients can't "ask" (that would be a read storm).

### Design
- Presence lives **in the gateway's memory** (ETS per node in Phase 2; a
  dedicated presence tier only if Phase 7 load tests demand it).
- State machine per user: `online → idle (10min no input) → offline`;
  dnd/invisible are client-declared. Idle detection: client heartbeat carries
  `last_activity`; gateway marks idle locally.
- Events: `PRESENCE_UPDATE {user, status, activities[], client_status}` —
  published to the guild fan-out path like any event, BUT generated by the
  gateway itself, not REST. (First place where the gateway *originates* events —
  note the architectural implication: it publishes to the bus.)
- The `GUILD_MEMBER_LIST_UPDATE` problem (Discord's deepest post on this — read
  it): a 100k-member guild's sidebar is a *windowed view* (online members +
  your pinned/hoisted groups), synced via "member list chunks". You'll
  implement a simplified version: groups = roles, client requests
  `REQUEST_GUILD_MEMBERS`, server streams chunks of 1000. Cap member lists at
  "online members only" — write down why Discord had to build lazy-loaded
  chunks (memory: full lists of 100k × every subscriber).

### Consistency stance (write this paragraph yourself)
Presence is allowed to be wrong for seconds. A user shows "online" after
crashing until heartbeat timeout (zombie window). Decide and document your
staleness budget per state. The lesson: **not all state deserves the same
consistency contract** — and deciding per-feature is the architect's job.

## 2. Typing indicators — the "easy" one (learn why it's designed exactly this way)

```
Client → gateway: {"t":"TYPING_START"}         (throttled client-side to 1/8s... Discord: 1/10s)
Gateway → guild fan-out: TYPING_START {channel_id, user_id, timestamp}
Client renders for 8s, no cancel message exists.
```
- **Fire-and-forget, no state, no cancel, no persistence.** If a TYPING_START
  is lost, the world heals in 8 seconds. This is a *self-healing ephemeral
  event* — the cheapest possible consistency model, chosen deliberately.
- Contrast with presence (sticky state, needs timeout+events) and messages
  (durable, needs ordering+resume). Three features, three consistency tiers.
  This comparison — written up — is the actual Phase 2 postmortem.
- Load lesson: 10 users typing in a 500-member guild = ~6 events/sec of pure
  noise. Rate-limit per (user, channel) server-side too (429 or silent drop —
  pick, defend it).

## 3. Read states / acks — the Rust service (Phase 8)

### The workload (from Discord's "Why Discord is switching from Go to Rust")
- Every user × every channel: `{last_read_message_id, mention_count}` — billions
  of rows, *tiny* each.
- Write pattern: every time you open a channel or scroll past mentions. That's
  a hot, random write storm — a few thousand writes/sec at real scale, at p99
  that must be low (it's on the "open channel" path).
- Discord's Go service (Fastly-built originally, then Go): fine at first, then
  **GC pauses → p99 latency spikes every 2 minutes** (large live heap → long
  mark/stop-the-world cycles). The Rust rewrite flattened p99. The famous
  graph in that post is one of the best systems-engineering figures ever
  published — go look at it now.

### Your build
1. **First in Go** (yes, Go first — the whole point is *measuring* the
   difference, not believing the blog post):
   - `read_states (user_id, channel_id) PRIMARY KEY, last_read_message_id, mention_count`
   - ScyllaDB-backed; writes are LWT-free upserts (random partition per user —
     even spread, that's why it scales).
   - API: `POST /channels/:id/messages/:mid/ack` (idempotent by design:
     last_read is a max — conflicting acks converge naturally. Another
     coordination-free pattern — collect them all in a list; this project
     keeps rewarding this trick.)
2. **Load test it**: sustained 5k acks/sec, 10M rows, p50/p99/p999 graphs,
   record GC pause timings (`GODEBUG=gctrace=1`, or runtime metrics →
   Prometheus). Observe sawtooth p99. (You may need a big heap to see it
   — tune GOGC down to force frequent GCs if your laptop is too fast.)
3. **Port to Rust** (axum or actix + scylla-rust-driver): same API, same
   tests, same load. Overlay the p99 graphs. Write the half-page postmortem:
   what did you actually gain, what did it cost in dev time, when is it worth it.
4. Bonus experiment: tune Go instead (GOGC, GC pacing, struct layouts to cut
   heap). How close can you get? (Discord's own conclusion included "we
   optimized Go for years first.") Honest engineering is comparing *both*
   escape routes.

### Integration
- Unread badges on the client = compare `last_read` vs latest message snowflake
  (both time-ordered — no DB hit needed client-side).
- `MESSAGE_ACK` event to *your own* sessions only (self-targeted fan-out —
  the gateway needs a per-user routing mode in addition to per-guild; add it
  to `01-gateway.md` §5's route table: `:user_id` as a "guild" key is the
  standard trick — Discord routes user events as a virtual guild. Document it.)
