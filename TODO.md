## 1. WebRTC SFU Video Stream Freeze / Black Screen
- **Symptom**: During screen sharing or camera toggle between peers (e.g., `atlas` and `hmida`), the receiver video tile is black or frozen, while audio continues working.
- **Root Cause (SFU production logs at `2026-10-09T02:21:44Z`)**:
  - SFU sends an initial downstream offer when a user shares video.
  - The client answers within ~200ms.
  - An automatic layer switch (`f` to `h` or `h` to `f`) queues a second downstream offer while the SFU signaling state is `have-local-offer`.
  - As soon as the first answer completes, SFU sends the second offer back-to-back.
  - In `client/src/lib/sfu-client.ts`, `applyDownstreamOffer` stashes the offer in `this.pendingOffer` because the PC is not yet in `stable` or is transitioning.
  - `flushPendingOffer()` only listens to the `signalingstatechange` DOM event. Since the transition to `stable` finishes without triggering another event, the stashed offer is orphaned and never answered.
  - SFU remains locked in `state=have-local-offer` indefinitely (for 44+ seconds), postponing all future video tracks and layer switches.
- [x] **Action Items**:
  - [x] **Client (`client/src/lib/sfu-client.ts`)**: In `stashDownstreamOffer(sdp)`, schedule a microtask/timer fallback (`setTimeout(() => this.flushPendingOffer(), 50)`) and check `this.pc.signalingState === 'stable'` to ensure pending offers always flush even if no further event fires.
  - [x] **SFU (`sfu/internal/router/router.go`)**: Add a safety timeout (e.g. 5–10s) when waiting for a subscriber's renegotiation answer to rollback or unwedge signaling state if an answer is dropped.
  - [x] **Tests**: Add unit tests in `client/src/lib/sfu-client.test.ts` for rapid back-to-back downstream offers.

## 3. File Uploads Failing (Mixed Content Blocked & Media Processing)
- **Symptom**: Uploading attachments (videos, images, files) fails with `Upload failed (network error)` or message send 500 / stuck in "Processing...".
- **Root Cause**:
  - Console error: `Mixed Content: The page at 'https://kith.moadabdou.me/' was loaded over HTTPS, but requested an insecure XMLHttpRequest endpoint 'http://kith.moadabdou.me/attachments/attachments/...'`.
  - The S3/MinIO presigned upload URL generated by the Go API uses `http://` scheme because `S3_USE_SSL` / `S3_PUBLIC_ENDPOINT_USE_SSL` was false or not respecting the public HTTPS scheme.
  - Messages 500 error: `attachments_message_id_fkey` constraint failure because messages are stored in ScyllaDB in production (`mode=scylla_only`).
  - Media worker was not started in deployment pipeline, and MinIO anonymous download/upload was missing on `attachments` bucket.
- [x] **Action Items**:
  - [x] Update S3 presigner client in `api/internal/media/storage.go` to ensure presigned URLs for `S3_PUBLIC_ENDPOINT` use `https://` when `S3_PUBLIC_URL` starts with `https`.
  - [x] Add reverse proxy route in nginx for `/attachments/`.
  - [x] Drop `attachments_message_id_fkey` in postgres and add migration.
  - [x] Set MinIO public access for attachments bucket and ensure `media-worker` runs in `deploy.sh`.
